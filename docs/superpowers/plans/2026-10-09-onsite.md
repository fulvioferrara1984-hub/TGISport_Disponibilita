# Blocco 3 — Deployment on-site: piano di implementazione

> **Per chi esegue:** SOTTO-SKILL RICHIESTA: superpowers:subagent-driven-development (consigliata) oppure superpowers:executing-plans. I passi usano le caselle (`- [ ]`).

**Obiettivo:** richieste di deployment on-site con posti TL/OP, accettazione dalla pagina operatore, presenze on-site che bloccano il remoto, compenso di trasferta nei riepiloghi, email di richiesta e di accettazione.

**Architettura:** un archivio Firestore a parte (`onsite/{id}`, compenso in `onsiteRiservato/{id}`) e un file di calcoli puri `app/onsite.js` (`DO.onsite`) usato da entrambe le pagine, dalla demo e dai riepiloghi. Le regole Firestore controllano posti, ruolo, stato e data; la demo (`app/demo.js`) replica le stesse condizioni e si prova con `node --test`. La dashboard aggiunge `app/onsite-admin.js` (richiesta e scheda del deployment); calendario, griglia, assegnazione, riepilogo ed esportazione leggono `DO.admin.onsite`.

**Tecnologie:** JavaScript nel browser senza framework, Firebase JS SDK 12.3.0, Firestore Security Rules v2, Google Apps Script V8, Node 26 (`node:test`, `node:vm`) per le prove.

**Spec:** `docs/superpowers/specs/2026-10-09-onsite-design.md`

## Vincoli globali

- Il compenso non arriva mai agli operatori: sta solo in `onsiteRiservato/{id}` (solo supervisori) e non compare nelle email agli operatori.
- Promemoria, orari per competizione, gettoni e finestra di blocco del remoto non si applicano all'on-site; le presenze on-site sono calcolate, mai scritte in disponibilità o eventi.
- Un abilitato `onsite: 'TL'` occupa solo posti TL, `'OP'` solo posti OP. Dopo l'accettazione l'operatore non si ritira dal sito.
- Si accetta solo con richiesta `aperta`, prima del giorno `da`, se destinatario, non escluso, non già dentro, con posti liberi nel proprio ruolo; la pagina blocca anche chi ha convocazioni remote `convocato`/`confermato` in quei giorni.
- `tariffaOnsite` predefinita 150 € al giorno; compenso proposto = giorni × tariffa.
- Testi fissati dalla spec (in italiano, neutri): «Richieste on-site», «Accetto», «Non posso», «Hai risposto: non posso», «Ho cambiato idea, accetto», «Hai già convocazioni il … : chiama il supervisore», «Posti esauriti», «Il supervisore ti ha tolto da questo deployment.», «Annullato dal supervisore», «On-site · <luogo>», «📞 Contatta il supervisore», «+ On-site», «Togli», «Modifica», «Chiudi richiesta», «Riapri», «Annulla deployment», «⛔ on-site», «⛔ in on-site», «… è in on-site a <luogo>: assegnare comunque?», «Tariffa on-site (€ al giorno)», «Ha accettato l'on-site · <luogo> <periodo> (<ruolo>)», «Non può per l'on-site · <luogo> <periodo>», «Richiesta on-site: <luogo> · <periodo>», «On-site accettato: <nome> · <luogo> <periodo>», «Rispondi sulla piattaforma».
- Prove: `node --test test/*.test.js`. Pubblicazione: `?v=17` → `?v=18` in `index.html` e `admin.html`; nuovi script `app/onsite.js` (entrambe le pagine, dopo `comune.js`) e `app/onsite-admin.js` (dashboard, dopo `convocazioni.js`). Il controllo `pre-commit` deve passare.

## Punti da sorvegliare in revisione

1. **Ultimo posto conteso** da due operatori: uno entra, l'altro riceve «Posti esauriti», mai entrambi — prova nel Task 2.
2. **Abilitazione tolta o cambiata dopo l'invio** (da TL a OP, o a «no»): la richiesta sparisce o mostra i posti del nuovo ruolo, e l'accettazione con il ruolo vecchio è rifiutata — prove nei Task 1 e 2.
3. **Deployment a cavallo di due mesi**: compenso diviso per giorno con totale esatto al centesimo, giorni on-site contati nel mese giusto — prove nei Task 1 e 6.
4. **Deployment annullato dopo le accettazioni**: giorni di nuovo liberi, niente presenze né compensi, scheda «Annullato dal supervisore» — prove nei Task 1 e 6.
5. **Convocazioni remote rifiutate o annullate negli stessi giorni**: non bloccano l'accettazione (solo `convocato`/`confermato`) — prova nel Task 1.

```
    // Deployment on-site: l'operatore vede solo quelli mandati a lui
    // e può solo occupare un posto del suo ruolo o dire che non può.
    function abilitazioneOnsite() {
      return get(/databases/$(database)/documents/operatori/$(mioOperatore())).data.get('onsite', '');
    }
    function primoGiornoOnsite() {
      let p = resource.data.da.split('-');
      return timestamp.date(int(p[0]), int(p[1]), int(p[2]));
    }
    function puoRispondereOnsite() {
      let io = mioOperatore();
      return operatore() && resource.data.stato == 'aperta' && request.time < primoGiornoOnsite()
        && io in resource.data.destinatari && !(io in resource.data.esclusi)
        && !(io in resource.data.accettatiTL) && !(io in resource.data.accettatiOP);
    }
    function accettaOnsite() {
      let io = mioOperatore();
      let ruolo = abilitazioneOnsite();
      return puoRispondereOnsite() && ruolo in ['TL', 'OP']
        && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['accettati' + ruolo, 'rifiuti'])
        && request.resource.data['accettati' + ruolo] == resource.data['accettati' + ruolo].concat([io])
        && request.resource.data['accettati' + ruolo].size() <= resource.data.posti[ruolo]
        && request.resource.data.rifiuti == resource.data.rifiuti.removeAll([io]);
    }
    function nonPossoOnsite() {
      let io = mioOperatore();
      return puoRispondereOnsite() && !(io in resource.data.rifiuti)
        && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['rifiuti'])
        && request.resource.data.rifiuti == resource.data.rifiuti.concat([io]);
    }
    match /onsite/{id} {
      allow read: if supervisore() || (operatore() && mioOperatore() in resource.data.destinatari);
      allow create, delete: if supervisore();
      allow update: if supervisore() || accettaOnsite() || nonPossoOnsite();
    }
    match /onsiteRiservato/{id} {
      allow read, write: if supervisore();
    }
```
